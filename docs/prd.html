Updated 12 Sep 2026 · after probing the live API

The mechanism changed. The idea didn't. This plan was written before the endpoint was tested. The live beta accepts vocabulary hints and ignores them. Output is byte-identical with and without, even on clips where the model mishears exactly the hinted word. So the lanes now vary the audio instead: untouched, faint noise, 200 ms of padding, 0.95× speed. The transcripts still disagree. The API is deterministic, so that disagreement comes from the transforms, not noise. The vote still settles it on per-word confidence. Vocabulary moved into the merge as a tie-breaker between spellings some lane actually heard.

Other measurements that overturn assumptions below: calls take 1.5–3.5 s, not 134 ms, though four lanes in parallel cost about 1.3× one call. No word timings are returned. On 20 real recordings, untouched audio scores 30.5% WER and the merge 16.7%, beating every single variant (the best scored 19.0%). The body of this document is the original plan, kept as written. The project README has the current design.

01Problem

Dictation is accurate on ordinary prose and unreliable on exactly the words that are slowest to type: colleagues' names, CLI tools, product nouns, internal jargon. kubectl comes back as "cube cuttle." The person dictating stops mid-flow to fix it, and the promised speed advantage evaporates.

The Dictation API already has the cure. Pass a list of expected terms alongside the audio and word error rate drops 10.2%, concentrated on precisely these names and identifiers. But the hint has to be chosen before the person speaks, and real speech is mixed-domain: one sentence holds a teammate's name, a deployment command, and plain English. Priming for one degrades the others — a lane primed with dev vocabulary will confidently turn "staging and" into "stagehand."

So the feature that fixes dictation is, in practice, unusable. Every product built on it has to guess a domain up front and eat the errors everywhere else.

02The mechanism

Don't guess — send the clip to every hint set at once. The endpoint answers in ~134 ms, so three calls issued in parallel cost roughly the wall-clock of one. Each response carries a confidence score for every individual word. Where the lanes disagree, the most confident phrase wins.

A · no hints push the cube cuttle·42 config to staging and tell prea·38
B · dev terms push the kubectl·94 config to stagehand·52 tell prea·39
C · contacts push the cube cuttle·45 config to staging and tell Priya·91
Quorum push the kubectl config to staging and tell Priya

Verified output of the aligner's test suite. Note that no individual lane is correct — B knows kubectl but breaks "staging and"; C knows Priya but not the tool. The merged line is a sentence none of the three returned.

Merging happens on phrases, not words. Lane B heard one word where A and C heard two, so word-by-word voting would let the two-vote majority "cube cuttle" survive. Grouping the disputed span first lets a single confident lane outvote a confident-sounding pair.

03Goals

  • Beat every single lane. On mixed-domain speech the merged transcript is more accurate than any one hint set applied alone.
  • Stay inside the typing illusion. Fanning out must not make the round trip feel slower than a single call.
  • Be self-evident. A viewer understands the mechanism from the screen alone, without narration.
  • Produce a number, not a vibe. Ship a word-error-rate table, measured on recorded audio with written ground truth.
  • Place in the top ten at the AssemblyAI Dictation hackathon.

04Non-goals

  • Not a system-wide dictation tool. No native overlay typing into the focused app — that needs accessibility permissions and would consume the entire budget. It would also hide the three lanes, which are the point.
  • No streaming or live partials. The endpoint is synchronous; push-to-talk means we own turn detection, which is an advantage, not a gap.
  • Hint sets do not adapt. Lane vocabularies are static config. Learning them from user corrections is a separate product.
  • No diarization or multi-speaker handling. One person, one microphone.
  • Exactly three lanes in v1. The aligner takes any N; the demo ships three, because three is the smallest number where voting means anything.

05User stories

The person dictating

  • As someone dictating a work note, I want a teammate's name and a CLI tool spelled correctly in the same sentence, so I don't stop to hand-fix either one.
  • As someone dictating, I want the transcript back in about the time one transcription takes, so speaking still beats typing.
  • As someone dictating, I want to see which words were contested, so I know where to glance before I trust the output.

The judge watching the demo

  • As a judge, I want to see the competing transcripts and the merged result together, so I understand the idea without a walkthrough.
  • As a judge, I want the latency cost of fanning out stated on screen, so I can tell whether the accuracy was bought cheaply.

Edges

  • When all three lanes agree, the output passes through unchanged and reports zero disputes.
  • When one lane errors or times out, the merge proceeds on the survivors rather than failing the request.
  • When no API key is present, the app runs on canned responses so the interface can be built without spending credits.

06Requirements

P0Push-to-talk capture

Given the mic is permitted, when the user holds the button or spacebar, then audio records until release and is encoded as 16 kHz mono PCM WAV. Clips shorter than 80 ms are discarded silently; clips are capped at 2 minutes.

P0Parallel fan-out

Given a recorded clip, when it is submitted, then all lanes are dispatched concurrently and the response reports both wall-clock elapsed and the sum of individual lane times, so the parallelism is visible rather than claimed.

P0Cross-lane word alignment

Given N transcripts of one clip, when aligned, then words are matched on combined text similarity and time-span overlap, tolerating differing word counts. Verified by test fixture where one lane returns 8 words and the others return 10.

P0Phrase-level dispute resolution

Given an aligned span where lanes disagree, when resolved, then the winner is scored on vote count and mean confidence together, and a lone high-confidence phrase can defeat a low-confidence majority. Spans of unanimous agreement are never rewritten.

P0Three-lane display

Given a completed merge, when rendered, then each lane's sentence appears aligned to the others with contested spans marked won or lost, and the merged sentence is the visual focus.

P0Accuracy measurement

Given a fixed set of at least 20 recorded utterances with hand-written ground truth, when evaluated, then the report gives word error rate for each lane alone and for the merge, on identical audio.

P1Live hint editing

The three vocabularies are editable in the interface, so a judge can add their own name and immediately hear it recognized.

P1Lane failure tolerance

A lane that errors or exceeds its timeout is dropped with a visible marker; the merge runs on whatever returned.

P2Audio-variation lanes

Fallback if hint parameters prove unavailable: lanes differ by gain normalisation and clip-boundary padding instead of vocabulary. Keeps the whole thesis intact on a different axis.

P2Calibrated lane weights

Per-lane confidence multipliers fitted on the eval set, correcting for a primed lane's tendency toward overconfidence. Hook already exists in the merge options.

08Open questions

Resolved

Does the beta host accept vocabulary hints, and under what parameter names?

No. Every hint field returns 200 and is ignored; output is byte-identical with and without. The lanes switched to the audio-variation axis (P2), and the thesis survived. Resolved 12 Sep.

Resolved

What is the concurrency limit, and does three calls per utterance fit the credit grant?

Concurrent calls run in parallel. Four lanes cost about 1.3× the wall-clock of one call. Resolved 12 Sep.

Open

Are confidence scores comparable across differently-primed lanes?

A lane primed with dev vocabulary may be confidently wrong on prose, which would bias every vote. Mitigation is already stubbed: per-lane weights fitted on the eval set. Resolve during implementation.

Resolved

Does the beta return per-word timings?

No. Per-word confidence is returned but no timings, so the merge detects this and aligns on text alone. Resolved 12 Sep.

Open

Is 20 utterances enough to claim a result?

Twenty is the floor for a credible slide; forty is better if recording time allows. Report the count alongside the number either way. Data — before the writeup.
